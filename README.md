# Практика 3: Классы и ООП в TypeScript

Каталог книг из Практик 2.1 и 2.2 написан в функциональном стиле: состояние живёт
в переменной `catalog`, а функции принимают его как параметр. В этой практике
вы перепишете его на классы: состояние и поведение окажутся в одном объекте.

Цель: почувствовать разницу между подходами и понять, когда классы уместнее функций.

## Что делать

Все правки — в `src/task6-classes.ts`. Полное задание с сигнатурами —
в комментарии в начале этого файла. Проверка: `npm test -- task6`.

### 1. Состояние `BookCatalog`

Приватный `books`, `readonly id`, конструктор `(id: string, books: Book[] = [])`.
Публичный API: `addBook`, `removeBook`, `getBooks`, геттер `count`.

Требования:
- `addBook` / `removeBook` не мутируют массив, а создают новый;
- `books` снаружи недоступен — внешний код не может присвоить его напрямую.

Тесты: конструктор, addBook, removeBook, getBooks, count.

### 2. Поиск и сортировка

`searchByTitle(query)` и `sortBy('year' | 'rating')`.
Логику заново не писать — переиспользовать `filterByTitle` и `sortBooks`
из `task5-utils.ts`.

Тесты: searchByTitle, sortBy.

### 3.  Интеграция в `main.ts`

Заменить функциональный каталог из Практик 2.1–2.2 на `new BookCatalog(...)`:

- `addBook(catalog, b)` → `catalog.addBook(b)`
- `removeBook(catalog, id)` → `catalog.removeBook(id)`
- `Object.values(catalog)` → `catalog.getBooks()`
- фильтры — `applyFilters(catalog.getBooks(), ...)`
- поиск — `catalog.searchByTitle(...)`, сортировка — `catalog.sortBy(...)`

### 4. Аудит кода

В проекте есть функции, которые написаны, экспортируются, но нигде не используются в `main.ts`

Ваша задача как разработчика:
Найдите все неиспользуемые функции в папке src/ (подсказка: IDE подсвечивает их серым цветом, или используйте поиск по проекту).
Заполните таблицу аудита в файле AUDIT.md (файл необходимо создать):

| Название функции | Где находится | Полезная ли она? (Да/Нет) | Как её можно использовать в будущем? (Идея для фичи) |
| :--- | :--- | :--- | :--- |
| calculateAverageYear | task5-utils.ts | Да | Показать в шапке сайта: «Средний год книг в коллекции: 2021» |
| ... | ... | ... | ... |


Решение:
Если функция полезная: оставьте её, но добавьте JSDoc-комментарий `/** @deprecated пока не используется, задел на фичу "Статистика" */`.
Если функция бесполезная (дублирует логику или делает странное): удалите её и её тесты.
Почему это важно: В реальных проектах «мёртвый код» (dead code) замедляет чтение и запутывает команду. Умение его находить и осознанно решать его судьбу — признак зрелого разработчика.

Что такое JSDoc-комментарий?

JSDoc — это стандарт оформления комментариев в JavaScript и TypeScript. Такие комментарии начинаются с /** (две звёздочки, а не одна) и заканчиваются */. Их особенность в том, что их понимает не только человек, но и IDE: VS Code читает JSDoc и показывает подсказки при наведении на функцию, а TypeScript использует их для проверки типов, если явные аннотации отсутствуют.
